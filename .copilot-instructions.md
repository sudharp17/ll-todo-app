# GitHub Copilot Instructions for Todo App

## Project Overview
This is a modern Todo application built with Next.js 15, React 19 RC, TypeScript, and Zustand for state management. The app uses Tailwind CSS for styling and Bun as the runtime/package manager.

## Architecture & Patterns

### Project Structure
```
app/
├── components/          # React components
├── lib/
│   ├── logic/          # Pure business logic functions
│   ├── store/          # Zustand state management
│   └── types/          # TypeScript type definitions
└── tests/              # Test files mirroring src structure
```

### Key Design Principles
1. **Separation of Concerns**: Business logic is separated into pure functions in `lib/logic/`
2. **Type Safety**: Comprehensive TypeScript usage with strict typing
3. **State Management**: Zustand for global state with provider pattern
4. **Component Architecture**: Small, focused, reusable components
5. **Testing**: Unit tests for both logic and store functionality

## Code Style Guidelines

### TypeScript
- Use strict TypeScript with explicit return types for functions
- Define interfaces for all data structures
- Use const assertions where appropriate
- Prefer `interface` over `type` for object shapes

### React Components
- Use function components with hooks
- Implement proper prop typing with interfaces
- Use "use client" directive only when necessary (client-side features)
- Follow Next.js 15 app router conventions

### State Management
- Use Zustand with provider pattern for SSR compatibility
- Keep store actions pure by delegating to logic functions
- Separate store interface from implementation

### Styling
- Use Tailwind CSS utility classes
- Follow responsive design patterns
- Use semantic color tokens (foreground, background, muted, border)

### File Naming
- PascalCase for components (`TodoItem.tsx`)
- camelCase for utilities and hooks (`todoLogic.ts`)
- kebab-case for configuration files

## Code Review Guidelines

### What to Look For

#### ✅ Good Practices
- **Type Safety**: All props, state, and function parameters are properly typed
- **Pure Functions**: Logic functions have no side effects and are easily testable
- **Component Composition**: Components are small, focused, and reusable
- **Error Handling**: Proper validation and edge case handling
- **Accessibility**: Semantic HTML and ARIA attributes where needed
- **Performance**: Proper use of React patterns (avoid unnecessary re-renders)

#### ❌ Code Smells
- Direct DOM manipulation in React components
- Business logic mixed into component code
- Missing TypeScript types or `any` usage
- Inline styles instead of Tailwind classes
- Mutating state directly instead of using immutable patterns
- Missing error boundaries for client components

### Specific Review Points

#### Component Reviews
```typescript
// ✅ Good: Proper typing and separation
interface TodoItemProps {
  todo: Todo;
  onToggle: (id: string) => void;
}

export function TodoItem({ todo, onToggle }: TodoItemProps) {
  // Component implementation
}

// ❌ Bad: Missing types, inline logic
export function TodoItem({ todo }) {
  const handleClick = () => {
    // Complex business logic here
  }
}
```

#### Store Reviews
```typescript
// ✅ Good: Delegates to pure functions
addTodo: (text: string) =>
  set((state) => ({ todos: addTodo(state.todos, text) })),

// ❌ Bad: Logic mixed in store
addTodo: (text: string) =>
  set((state) => ({
    todos: [...state.todos, { 
      id: Math.random().toString(), // Impure!
      text,
      completed: false 
    }]
  })),
```

#### Logic Function Reviews
```typescript
// ✅ Good: Pure, testable, well-documented
/**
 * Adds a new todo to the list
 * @param todos - Current list of todos
 * @param text - Text for the new todo
 * @returns New array with the added todo
 */
export function addTodo(todos: Todo[], text: string): Todo[] {
  if (!text.trim()) return todos;
  // Pure implementation
}

// ❌ Bad: Side effects, unclear behavior
export function addTodo(todos, text) {
  todos.push({ text }); // Mutation!
  return todos;
}
```

### Testing Requirements

#### Unit Tests Should Cover
- All business logic functions with edge cases
- Store state transitions
- Component behavior and user interactions
- Error handling scenarios

#### Test Structure
```typescript
// Follow AAA pattern: Arrange, Act, Assert
describe('addTodo', () => {
  it('should add a new todo with generated ID', () => {
    // Arrange
    const todos: Todo[] = [];
    const text = 'New todo';
    
    // Act
    const result = addTodo(todos, text);
    
    // Assert
    expect(result).toHaveLength(1);
    expect(result[0].text).toBe(text);
  });
});
```

## AI Assistant Guidelines

### When Suggesting Code
1. **Follow the established patterns** in the existing codebase
2. **Maintain type safety** - always provide proper TypeScript types
3. **Keep business logic pure** - suggest logic functions that are testable
4. **Use existing utilities** - leverage `generateId()`, existing types, etc.
5. **Follow Next.js 15 conventions** - app router, server/client components

### When Reviewing Code
1. **Check for type safety** - flag missing types or `any` usage
2. **Verify separation of concerns** - logic should be in `lib/logic/`
3. **Ensure immutability** - state updates should be immutable
4. **Validate accessibility** - suggest improvements for a11y
5. **Consider performance** - identify potential optimization opportunities

### Common Suggestions
- Add JSDoc comments for complex functions
- Suggest test cases for new functionality
- Recommend error boundaries for client components
- Propose accessibility improvements (ARIA labels, keyboard navigation)
- Identify opportunities for component composition
